# AGENTS.md — ProofSec (root policy, read by every agent)

ProofSec is a programmable USDC escrow on Solana for offensive-security engagements
(pentest / audit). Hackathon MVP (Superteam Brasil / Colosseum), **devnet only**.

This file is loaded by Antigravity, Claude Code, Kiro, Codex and any AGENTS.md-aware tool.
Nested `AGENTS.md` files add rules for their area; they never relax rules here.
Keep this file under 8 KB: Codex stops reading at 32 KiB combined and drops the
deepest (most specific) files first.

## 2. Invariants — never break them, never work around them

- **INV-1** Solana is the source of truth for funds, status and hashes. DynamoDB is a
  mirror plus metadata; when they disagree, the chain wins.
- **INV-2** No component custodies funds. The backend holds no wallet keys. The agent
  executor key can only move company funds into company-owned escrows, within the
  on-chain `AgentPolicy` limits.
- **INV-3** The LLM never decides amounts, recipients, deadlines or approvals. Budgets
  come from `backend-serverless/functions/common/policy.py`; limits are enforced on-chain.
- **INV-4** Funds can always leave an escrow through public rules (approve, claim after
  review window, arbiter resolution, refund after deadline, cancel before accept).
  Anything that can lock funds forever is a **Critical** bug.
- **INV-5** Payouts go only to the ATA of the on-chain researcher / treasury / client.
  Never accept a client-supplied payout account.
- **INV-6** Reports are encrypted in the browser; the backend never sees plaintext.
  The S3 object key is derived from the on-chain evidence hash.
- **INV-7** The IDL is generated by `anchor build` and copied by
  `contracts/scripts/sync-idl.mjs`. Never hand-edit `frontend/src/idl/` or `agent/idl/`.
- **INV-8** API identity comes from the Lambda authorizer (SIWS → JWT), never from
  the request body.

Changing an invariant is an architecture change → follow §6.

## 3. Rule tiers

- **MVP — mandatory now:** the invariants; on-chain authorization for every
  value-moving instruction; adversarial tests for every program instruction; no secrets
  in git; human approval for §5; a `docs/decisions.md` entry for design changes.
- **Production — tracked, not blocking the demo:** CloudTrail, full alarm coverage,
  budgets, PITR, separate AWS accounts, CI gates, tested disaster recovery, external audit.
  Record gaps in `docs/security-review.md` instead of blocking work.
- If a production-tier item is cheap and safe (log retention, a narrower IAM policy),
  just do it.

## 4. Orchestration protocol

1. One agent per area at a time; one branch or worktree per task.
2. Every task ends with a **handoff note**: what changed, tests run, open risks,
   docs updated. The author of a change never reviews it.
3. **Cross-area contracts** — change all consumers in the same task, or split into
   coordinated tasks:
   - the IDL (owned by `contracts/`);
   - the JobAccount byte layout (decoded in `backend-serverless/functions/common/solana.py`);
   - the HTTP API (`backend-serverless/template.yaml` ↔ `frontend/src/lib/api.ts`, `agent/core.ts`).
4. Kiro specs (`.kiro/specs/*`) must reference `docs/` rather than duplicate architecture.
5. **Tool loading:** keep shared rules in `AGENTS.md` files only. Do not add a `CLAUDE.md`
   (it makes Claude Code stop reading `AGENTS.md`, including nested ones). Do not use
   `AGENTS.override.md` (Codex) or `.agents/` (Antigravity) for shared rules; other tools ignore them.
6. Findings use the format in `docs/security-review.md` (ID, severity, component, file,
   scenario, impact, remediation, verification, owner, status).

## 5. Human approval

**Allowed without approval (dev/devnet only):** `anchor build`, `anchor test`,
`anchor deploy --provider.cluster devnet` with the dev wallet, `sam validate`,
`sam build`, `sam deploy --no-execute-changeset` on the dev stack, local tests.

**Requires explicit approval:**
- executing a CloudFormation changeset or deploying any non-dev stack;
- IAM changes, deleting stacks, tables or buckets, `sam delete`;
- changing the program upgrade authority or the `Config` admin / arbiter / treasury;
- anything on mainnet or involving real funds;
- disabling a security control, test or alarm;
- `git push --force`, history rewrites, `rm -rf` outside build directories.

When uncertain: **STOP, explain the risk, ask.**

## 6. Change management

- Before changing security-sensitive code read `docs/architecture.md`,
  `docs/program-design.md` and `docs/threat-model.md`.
- Never silently redesign. If implementation needs an architectural change: stop, add a
  *Proposed* entry to `docs/decisions.md` (Decision / Reason / Alternatives / Security
  impact / Operational impact) and wait for approval.
- No unrelated refactors. Small commits: `feat:`, `fix:`, `test:`, `security:`, `infra:`, `docs:`.
- Every confirmed vulnerability gets a regression test that is never deleted.

## 7. Secrets and wallets

Never commit or paste into prompts: keypairs (`id.json`, `agent-keypair.json`),
seed phrases, `.env*` files, the JWT secret, the agent API key, LLM keys, AWS credentials.
Never ask for seed phrases. Use dev wallets only; no real funds. Runtime secrets live in
SSM Parameter Store (SecureString) — see `backend-serverless/AGENTS.md`.

## 9. Definition of done (MVP)

- Tests pass: happy path, unauthorized signer, wrong account, wrong state, boundaries.
- Invariants intact.
- Independent review done.
- Docs updated: `docs/program-design.md` invariants, `docs/decisions.md`, `docs/security-review.md` status.
- Handoff note written.
